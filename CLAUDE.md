# OneRingDB

Card database for the *Lord of the Rings* Trading Card Game (LOTR TCG). Symfony 8.1 app, PHP >=8.5, Doctrine ORM ^3.2 / DBAL ^4, PostgreSQL 16.

## Dev environment

Docker Compose stack at `docker/dev/compose.yaml`: `symfony` (app + built-in web server on :8080), `postgres` (:5432), `pgweb` (:8081, DB browser UI).

The `Makefile` wraps everything through `docker-compose -f docker/dev/compose.yaml exec symfony`:

- `make up` / `make down` — start/stop the stack
- `make install` — composer install
- `make shell` — shell into the symfony container
- `make lint` — `lint:container` + ecs --fix + rector + phpstan
- `make test` — `bin/phpunit`
- `make ci` — lint + test
- `make db` — drop/recreate schema and load fixtures, then clears the Doctrine L2C filesystem cache (see below) for both `--env=dev` and `--env=test`. This step was added after a schema reset once let a new `Ruleset` reuse an old, since-deleted one's auto-increment id and get served its stale cached `cards` collection (`RulesetServiceIntegrationTest` failures right after regenerating fixtures) — if you ever bypass `make db` and reset the schema some other way, clear `doctrine.second_level_cache_pool` manually (both envs) afterwards.

## Testing

- PHPUnit 11, config in `phpunit.dist.xml`, tests under `tests/`, mirroring `src/` (`Controller/`, `Repository/`, `Service/`, `Enum/`, `SearchQueryBuilder/`).
- Functional/controller tests extend `WebTestCase`; repository/service tests extend `KernelTestCase`.
- `framework.test: true` is enabled in the test env, so `static::getContainer()` exposes private services too.
- Web profiler is installed in test env but `framework.profiler.collect` is `false` by default — call `$client->enableProfiler()` **before** a request to collect data (e.g. to read query counts from the `db` collector afterwards). It must be called again before each request you want profiled; it resets after each request.
- `tests/DoctrineCollector.php` (trait) — reuse `assertDoctrineQueryCount(int)` instead of re-deriving query-count assertions from the profiler's `db` collector. Used by `CardControllerTest`, `HomeControllerTest`, `CultureControllerTest`, `PublishedSetControllerTest`.
- `tests/TranslationCollector.php` (trait) — `assertNoMissingTranslations()` reads the profiler's `translation` collector. Every functional page test (`CardControllerTest`, `HomeControllerTest`, `CultureControllerTest`, `PublishedSetControllerTest`, `SearchControllerTest`) has a `testNoMissingTranslationsOn...Page` test using it — add one for any new page controller.

## Architecture notes

- Routes: `app_home` (`/`), `app_card` (`/card/{id}`), `app_published_set` (`/set/{set}`), `app_culture` (`/culture/{culture}`), `app_search_form` (`/search`), `app_search_cards` (`/cards`). Set and culture pages both forward into `SearchController::search`.
- `PublishedSet` was renamed from `Pack`, and the `Card`↔`PublishedSet` relation was changed from many-to-many to many-to-one (one set per card). See git history (`ce00c77`, `b5ed854`) for the migration.
- Doctrine second-level cache (L2C) is enabled globally (not just prod) via the `doctrine.second_level_cache_pool` cache pool (`config/packages/cache.yaml`, adapter `cache.app` — filesystem, persists across requests/kernel reboots/`make db` resets, including between two functional-test requests hitting the same var/cache dir). It's a distinct pool/namespace from `cache.app` itself, so `cache:pool:clear cache.app` does **not** clear it — use `cache:pool:clear doctrine.second_level_cache_pool`. Symptom of stale entries: a `setCacheable(true)` query (e.g. `getCard()`) keeps returning results (or `null`) that don't match the current DB content, e.g. right after reloading fixtures or changing the active `Ruleset`.
  - `Card` and `PublishedSet` entities are marked `#[Cache(usage: 'NONSTRICT_READ_WRITE')]` (not `READ_ONLY`: the EasyAdmin CRUD controllers need to persist ORM-level updates to them, and `READ_ONLY`'s persister throws on any update — see below). This is a deliberate trade-off: nothing currently stops an admin from editing a `Card` row in place instead of creating a revision via `CardService::duplicate()`, which is how the errata system is meant to record changes.
  - `CardRepository::getCard()` (used by `/card/{id}`) explicitly sets `->setCacheable(true)` on its query — on a cache hit this avoids hitting the DB entirely.
  - `CardRepository::search()` (used by `/cards`, `/set/{set}`, `/culture/{culture}`) explicitly sets `->setCacheable(false)` — search results are never L2C-cached, so these pages always issue live queries.
  - `PublishedSetService::all()` (backs the "Sets" dropdown, including on the homepage) uses a plain `findBy()` — not cacheable either.
  - `Ruleset` is also `#[Cache(usage: 'NONSTRICT_READ_WRITE')]`, for the same reason: `isActive` is updated via the ORM in `RulesetService::activate()`. The `Card::$rulesets` / `Ruleset::$cards` ManyToMany association is *also* `#[Cache(usage: 'NONSTRICT_READ_WRITE')]` on **both** sides (Doctrine requires both the association and its target entity class to be cacheable, or it throws `NonCacheableEntityAssociation`) — this is what lets `CardController`'s revision-history table (`RulesetService::findRulesetHistory()`, iterating `Card::getRulesets()` per revision) cost 0 queries on a cache hit instead of one lazy-collection query per revision (N+1).
    - **Corollary**: any code that changes `card_ruleset`/`ruleset` rows *without* going through the ORM (raw SQL) bypasses this cache's automatic invalidation and must evict it manually: `$entityManager->getCache()?->evictCollectionRegion(Card::class, 'rulesets')`. This is cheap (`Region::evictAll()` clears the whole cache-pool namespace for that association, not a per-row walk) — see `RulesetService::createRuleset()` below, and the `tearDown()` of `tests/Service/*IntegrationTest.php`, which both do this after raw SQL. Forgetting it after a raw SQL mutation causes hard-to-spot stale-cache bugs (already hit once: a test's raw-SQL cleanup leaked stale Rulesets into an unrelated test's revision-history count).
- The homepage (`hide_menu`/`hide_search` = true) skips the navbar's menu/search form but renders its own culture/set dropdowns directly in `home/index.html.twig`, calling the same `cultures.all()` / `sets.all()` Twig globals.
- `Card::$position` (nullable int) holds the card's rank within its `PublishedSet`, populated from the fixture JSON's `card_number` (`RulesetFixtures`, via the snake_case→camelCase name converter: `card_number` → `DtoCard::$cardNumber`). No longer unique per `(published_set_id, position)` at the DB level — a card revision (see below) shares the same set/position as the version(s) it supersedes; uniqueness among *visible* cards is enforced by the active-Ruleset filter instead.
  - `CardRepository::findPreviousCard()` / `findNextCard()` use it to find the adjacent card in the same set (return `null` at a set boundary or when `position` is `null`); both are `->setCacheable(true)` (same L2C pattern as `getCard()`) so they add zero queries on a cached second visit. Both also filter by the active `Ruleset` (see below).
  - `CardController` passes `previousCard`/`nextCard` to `card/index.html.twig`, which renders the prev/next links (absent when `null`).
- `Card::getFullTitle()` prefixes the title with `Card::UNIQUE_SYMBOL` (`•`) when `isUnique()` is true — there is no `getFullName()` on `Card`, `getFullTitle()` (title + optional subtitle) is the method to extend for title-rendering changes.
- **Errata/Ruleset**: `Ruleset` (`id`, `name`, nullable `isActive`, nullable `publicationDate`) is ManyToMany with `Card` (owning side on `Card`, join table `card_ruleset`) and represents a state of the game's rules. A DB-level unique constraint on `ruleset.is_active` guarantees at most one active `Ruleset` at a time (multiple `NULL`s are allowed by standard SQL unique-index semantics, only a second `true` would collide). `publicationDate` follows the same nullable-`\DateTime`-copied-on-set pattern as `PublishedSet::$release_date` (defensive `DateTime::createFromInterface` copy in the setter) — the seed `Ruleset` uses `2001-11-06`, the LOTR TCG's real launch date (same date as `PublishedSet` "01"'s `release_date`).
  - `findPreviousCard()`, `findNextCard()`, and `SearchQueryBuilder::buildQuery()` (backs `CardRepository::search()`, so `/cards`, `/set/{set}`, `/culture/{culture}`) inner-join `c.rulesets` and filter `r.isActive = true` — browsing/search/prev-next-navigation only ever surfaces the currently active revision of each position. `CardRepository::getCard()` (backs `/card/{id}` and its modal route) deliberately does **not** filter by Ruleset: a Card page must open by id even for a superseded revision (reached via an old link, or a row in its own revision-history table) — direct-by-id lookup is intentionally exempt from the "only the active Ruleset is visible" rule that governs discovery.
  - `Card::$id` embeds a revision suffix: `{setNumber}{cardNumber}.{revision}`, e.g. `01001.0` for the first printing of the first card. `Card::$revision` (int, defaults to `0`) is the same number as a real, queryable column — it's kept in sync with the `.{revision}` suffix of `$id` by whichever code builds the id (`RulesetFixtures`, `CardService::duplicate()`), it is not derived automatically. An errata card reuses the same `PublishedSet`/`position`/`title`/`subtitle` as the card it revises, gets the next revision number in its id (`01001.1`, ...), and is linked to a different `Ruleset` instead of the original one — the two `Card` rows coexist, and only the one linked to the active `Ruleset` is ever returned.
  - The external card image URL (`lotrtcgwiki.com/wiki/_media/cards:lotr{code}.jpg`) is built from the bare `{setNumber}{cardNumber}` code, not `Card::$id` — it must never include the revision suffix.
  - **Fixtures layout**: `fixtures/rulesets/<date>/ruleset.json` (`{"name": ..., "date": "YYYY-MM-DD"}`) + `fixtures/rulesets/<date>/cards/*.json` (one file per `Card`, same shape as before: `set_number`, `card_number`, `rarity`, `name`, `type`, `game_text`, ... → `DtoCard`). The folder name is just the date for readability — `RulesetFixtures` sorts folders by `ruleset.json`'s `date` field alone, not by folder name or directory-listing order. Only the *oldest* Ruleset's `cards/` folder holds every Card (~1839 in the real fixtures); every later Ruleset's folder holds only the Cards it introduces or revises (matched by `set_number`+`card_number`, no explicit "supersedes" field in the JSON). `RulesetFixtures::load()` carries the latest known `Card` per code forward from one `Ruleset` to the next in an in-memory map, replacing an entry (new `Card`, `revision` = old + 1) whenever the new Ruleset's folder redeclares that code — so **every** `Ruleset`, not just the active one, ends up complete (one `Card` per known position). The *most recent* Ruleset (by date) is the one marked active.
    - Per `Ruleset`: persists the `Ruleset` and that folder's new/revised `Card`s via the ORM (needed for their enum/subclass field mapping), `flush()`es so both have real ids, then bulk-inserts that `Ruleset`'s entire `card_ruleset` row set (carried-over + replaced entries from the in-memory map) with a single multi-row `INSERT` via the DBAL connection (`$manager->getConnection()`) instead of one `addCard()` per Card. This is what made `make db` fast enough to drop the `-d memory_limit=-1` it used to need — see the L2C corollary above for why looping `addCard()` over ~1839 Cards × 7 Rulesets was so much slower.
  - `CardService::duplicate(Card, ?int $revision = null)` clones a `Card` (same concrete subclass, same content) under a new id: same code (rebuilt from `$card->getPublishedSet()->getPosition()` + `$card->getPosition()`, not parsed from `$id`), revision `$card->getRevision() + 1` by default. The duplicate starts with an empty `$rulesets` collection — it's not linked to the original's Ruleset(s); link it via `Ruleset`/`RulesetService::swapCard()` explicitly.
  - `CardService` is still not wired into any controller/command, so it's absent from the compiled container — `CardServiceIntegrationTest` must instantiate it manually from container-fetched dependencies rather than `$container->get(CardService::class)`. `RulesetService` *is* now wired (into `CardController`, see below), so it doesn't need that workaround. `RulesetService` has:
    - `findRulesetHistory(Card)` — every Ruleset a Card (in any revision) has been linked to, oldest first, each paired with the revision that was active under it (`list<array{card: Card, ruleset: Ruleset}>`); built from `CardRepository::findRevisions()` (every Card sharing the same PublishedSet+position). Backs the revision-history table on `/card/{id}` (`card/index.html.twig`, below the card detail block): each row links to that revision's page unless it's the one currently displayed.
    - `findMissingPositions(Ruleset)` / `isComplete(Ruleset)` — completeness check. "Known positions" of a `PublishedSet` are derived from `CardRepository::findDistinctPositions()` across *all* Cards of that set regardless of Ruleset (not `PublishedSet::$size`, which is `null` for every fixture set today).
    - `createRuleset(string $name, ?Ruleset $baseRuleset = null)` — creates a new, inactive `Ruleset` and links it to every `Card` of the base Ruleset (the active one by default). Used as the starting point for drafting an errata Ruleset before individual `Card` revisions get swapped in. Copies the ~1839 `card_ruleset` rows with a single `INSERT ... SELECT` (raw SQL via the DBAL connection) rather than one `addCard()` per Card — looping through the ORM would touch (and L2C-cache-write) every Card's `$rulesets` collection individually, which is slow enough to matter at this volume (was the difference between a ~13s and a ~51s full test run). Evicts the `Card::$rulesets` collection region afterwards (see the L2C corollary above) and `refresh()`es the new `Ruleset` so its `$cards` collection lazy-loads the copied rows instead of staying empty.
    - `swapCard(Ruleset, Card $oldCard, Card $newCard)` — replaces `$oldCard` with `$newCard` in a Ruleset, in one DB transaction (`EntityManagerInterface::wrapInTransaction()`, which flushes and commits, or rolls back and closes the EM on error).
    - `activate(Ruleset)` — checks `isComplete()` first (throws before touching the DB otherwise), then, in one transaction, deactivates the previously-active `Ruleset` with its own `flush()` before activating the target one with a second `flush()`. The two flushes must stay in that order and separate: Postgres checks the unique constraint on `ruleset.is_active` per-statement (not deferred), so both `UPDATE`s landing in one flush could hit the constraint depending on Doctrine's unspecified change-set ordering.
  - Integration tests for these services (`tests/Service/*IntegrationTest.php`) persist real rows against the dev DB — this project has no transactional test isolation (no DAMADoctrineTestBundle) — so each has a `tearDown()` that deletes what it created. `RulesetServiceIntegrationTest` additionally captures the originally-active `Ruleset`'s **id** in `setUp()` and restores it as active in `tearDown()`, in case a test activated (and left behind, now-deleted) another one — restore by id, not by a hardcoded fixture name: which `Ruleset` is the seed/active one is fixture data, not a stable constant (it already changed once, from a single "Decipher Standard Rules" Ruleset to the multi-Ruleset layout above).
- `src/Twig/CardTextExtension.php` provides the `card_markup` Twig filter (auto-registered via `autoconfigure: true`, no manual service wiring needed): transforms `<keyword>`/`<phase>` tags in `card.text` into `<span class="keyword">`/`<span class="phase">` (styled bold in `assets/styles/app.css`) and applies `nl2br`. Used in `templates/component/_card_effect.html.twig` instead of the plain `nl2br` filter. No HTML-escaping is done — card text is trusted fixture data. Extend the `str_replace` pairs in `markup()` to support more tags later.
